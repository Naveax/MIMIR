whether Rust type shaping and narrow implementation were added, and why
- Yes.
- Added shared DTO-like contracts in `crates/mimir-types/src/lib.rs` because later solver,
  validator, or adjacent crates may need to consume the canonical/event/phase boundary as plain
  data.
- Added narrow family-specific transformation logic in `crates/mimir-skill/src/lib.rs` because
  the work is Skill Forge logic, not replay parsing and not shared runtime orchestration.
- No new crate was created because the existing crate split already matches the ownership
  boundary.

why this is enough for the next parameter-solver/variation pass
- The next pass now receives one explicit, deterministic low-boost-recovery seed boundary instead
  of a vague replay slice plus implied semantics.
- Solver work can start from a fixed subject/window/provenance linkage and one candidate phase
  window without pretending contact or low-boost truth is already solved.
- Variation work can stay bounded to that same family-specific candidate window and does not need
  to reopen canonicalizer ownership.
