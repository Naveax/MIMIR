3) Stage77 surfaces intentionally deferred from this batch

- branch payload canonical reload parity proof
  Status before batch: partially closed but not independently missing
  Why deferred: current Stage77 runtime output and canonical result both consume the same `load_export_bundle -> adapt_loaded_export_for_consumer` path. Adding a separate “parity” test would mostly restate the same loader output and would not harden a distinct boundary.

- broader persisted-input negative drift for optional/defaulted proposal fields (`actions`, `legal_hint`, `metadata`)
  Status before batch: partially open
  Why deferred: current persisted contracts intentionally default those fields on deserialization. Tightening that into a loader failure in this pass would widen semantics beyond a bounded Stage77 closure batch. The batch closed the required-field failure path and the downstream exported-payload negative guard without changing loader semantics.

4) Why each deferred item was deferred

- canonical reload parity was deferred because there is no separate consumer implementation to cross-check; the current runtime and canonical reader already share the same loader, so another parity test would be tautological.
- optional/defaulted persisted-input proposal-field drift was deferred because changing the defaulting contract would be a contract change, not a narrow closure test.
